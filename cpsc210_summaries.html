Part 1: Foundations

How do we write a program and know it is correct?

1. Learning a New Language

ImportantCore idea

TypeScript is CPSC 110’s design method with two changes: types the compiler checks (enforcement) and control flow written as statements (form).

What does the type checker buy you?

It rejects type mistakes before the program runs. Every parameter1 and return value2 is annotated with a type. Before anything runs, the compiler tsc3 checks every use against those types and refuses to produce a runnable program until the mismatches are fixed.

An error caught this way, before the program runs, is a static error4. In ISL and Python the same mistake is a runtime error5: it surfaces only while the program runs, and only if that line happens to execute.

Then why still test?

Because the compiler cannot know what happens when the program runs on a given input. It works on the static view6: the source text, read without executing it. Which branch an if takes, and what a variable holds, are facts of the dynamic view7, decided during a run. If letterGrade(95) returns "A" where the spec says "A+", the types are fine and only a test that runs the call finds it. Static checking “never removes the need to run and test a program.”

Why does the order of if checks matter?

Because return exits at once, so the first true condition wins. A statement8 performs an action (deciding, returning) and produces no value; an expression9 evaluates to a value. ISL’s cond is an expression; TypeScript writes the same logic as a chain of statements:

function letterGrade(score: number): string {
  if (score >= 80) {
    return "A";           // 95 is caught here and never reaches the checks below
  } else if (score >= 68) {
    return "B";
  } else if (score >= 55) {
    return "C";
  } else if (score >= 50) {
    return "D";
  } else {
    return "F";
  }
}

Why divide last?

To keep the values whole for as long as possible. number is binary floating point10: a single numeric type stored as a binary approximation, so most decimals are inexact, as \(1/3\) is in decimal. (11 / 20) * 100 gives 55.00000000000001; (11 * 100) / 20 gives exactly 55, “because the multiplication happens while the values are still whole numbers.” For the same reason, be careful comparing computed decimals for exact equality. Note also that / never truncates: 7 / 2 is 3.5.

Why () => f(x) and not f(x) in a test?

So that checkExpect decides when the call runs. In

test("Score of 88 returns an A", checkExpect(() => letterGrade(88), "A"));

the first argument to checkExpect is a thunk11: a function of no parameters that wraps a computation to be run later. Don’t add braces: () => { letterGrade(88) } returns nothing, so the check compares undefined with "A" and fails. In Part 1 each test case holds exactly one checkExpect.

If a program type-checks, what exactly do you know about it, and what don’t you know?

2. Modelling With Types

ImportantCore idea

Describe the shape of the information as a type; functions then follow that shape.

Where do you start?

With the data12, not the code. The textbook’s process: identify the entities \(\to\) the distinct cases \(\to\) the information each case needs \(\to\) translate into a type \(\to\) write concrete examples \(\to\) look for generalisation. Name each value with const name: Type = value; a const name can never be reassigned.

Which building block fits?

The one that matches the shape of the information:

Shape of Information Type Building Block
One atomic fact A primitive: number, string, boolean
A fixed set of choices Union of literals13, a type whose values are exactly the listed literals: "red" | "green" | "yellow"
Facts that belong together An object type: type Song = { title: string; artist: string; durationSeconds: number }
One of several cases Tagged union14, a union of one object type per case, each carrying a shared discriminator (kind) set to a different constant
Data of any length A type that refers to itself
One shape for many element types Generics15: a type parameter, as in LinkedList<T>. “Use generics only when you see real duplication.”

How does the type shape the function?

One branch per case, and a recursive call16 wherever the type refers to itself. Checking kind narrows17 the type: after p.kind === "songs" the compiler knows p.first and p.rest exist, and it rejects p.first in the "empty" branch.

type Playlist = { kind: "empty" } | { kind: "songs"; first: Song; rest: Playlist };

function totalDuration(p: Playlist): number {
  if (p.kind === "empty") {
    return 0;                                                  // base case
  } else {
    return p.first.durationSeconds + totalDuration(p.rest);    // the type refers to itself here
  }
}

What’s the difference between null and undefined?

null18 represents a deliberate “no value here”, such as a lookup that finds nothing. undefined19 is the value a name has when nothing has been assigned to it yet. The textbook later notes that built-in operations such as find use undefined for “not found”.

Why === and never ==?

Because == converts types before comparing: 1 == "1" and true == 1 are both true. These surprises are never visible statically. === is strict: 1 === "1" is false.

What can’t a type say?

That a value is meaningful. durationSeconds: number accepts -30, so the textbook records “must be positive” in a comment and relies on tests. That gap is Chapter 3’s subject.

3. Checking Invariants

ImportantCore idea

An invariant20 is a property that must hold for a value or computation to be meaningful; in this course, one the type system cannot express. Document it, test it, assert it.

Where do invariants attach to a function?

To its inputs and its output. A precondition21 is an invariant that must be true of the arguments when the function is called (daysLate is a whole number and >= 0). A postcondition22 is what the function guarantees about its result, assuming the precondition held (the fee is between 0 and 10). Together they form the function’s contract23: the caller promises the preconditions, the function promises the postconditions. Both go in the JSDoc doc comment. A useful invariant is precise, testable and operational: “daysLate is reasonable” is none of these.

Why write tests before the code?

So that a passing test means something. First write a stub24: the right signature returning a clearly wrong value (lateFee returns -1, which no real fee can equal). Every test must fail against it, because “a test that cannot fail checks nothing.” Then implement. Tests derived from the spec caught the textbook’s missing $10 cap; “tests written after tend to mirror the code, mistakes included.”

Which inputs?

One representative of each equivalence class25, plus every boundary value26. An equivalence class is a group of inputs that the spec says should be handled the same way. The classes come from the spec, never from paths through your code: a buggy implementation sends lateFee(12) and lateFee(30) down the same path, but the spec separates them. A boundary value is the last input on each side of an edge between classes: for lateFee, 2/3 and 21/22. Off-by-one faults (<= 3 for <= 2) show up only at those inputs.

Should you test inputs that break a precondition?

Not as an equivalence class: the precondition defines the input space, so lateFee(-5) is a meaningless input, not a missing class. But the function can refuse to continue. An assert27 checks a condition and terminates the program, printing a description, when it is false. When a function asserts its precondition, the textbook tests the assert with checkError.

Is every failure a bug?

No. An expected error is a foreseeable outcome that belongs in the contract, like renewing a loan with no renewals left. An unexpected error means an invariant has been violated, like a loan with renewalsRemaining of -1, which no correct sequence of operations can produce.

Expected Error Unexpected Error
Return a Result; test the returned value with checkExpect assert halts; test with checkError, which passes only if an error occurs

Result<T, E>28 is a tagged union, { ok: true, value: T } | { ok: false, error: E }, so the type checker can see whether failures are handled. Rule of thumb: “if the specification describes the outcome, check the outcome; if the outcome should be impossible, check that the program halts.”

function renew(loan: Loan): Result<Loan, string> {
  assert(loan.renewalsRemaining >= 0, "Loan invariant violated: negative renewals");
  if (loan.renewalsRemaining === 0) {
    return { ok: false, error: "No further loan renewals available" };   // expected
  }
  return { ok: true, value: { title: loan.title, renewalsRemaining: loan.renewalsRemaining - 1 } };
}
test("renewal is refused when no renewals remain",
  checkExpect(() => renew(exhausted), { ok: false, error: "No further loan renewals available" }));
test("renew halts on a corrupted loan", checkError(() => renew(corrupted)));

Why need types, tests and assertions?

Because each covers the others’ gaps. Types check structure statically, before the program runs; tests probe chosen inputs from outside; assertions watch invariants from inside, on every execution that reaches them. “An invariant that lives only in someone’s head cannot be checked by anything.”

4. Maintaining Invariants

ImportantCore idea

Make invalid values impossible to create, not merely detectable.

When does an invariant always hold?

When two things are true: it is established29 when the value is created, and preserved30 by every operation that produces a new value from an old one. Then every value that ever exists is valid.

Isn’t a constructor function enough?

No. makeAccount(balance) asserts balance >= 0, but “the protection is only a convention”: a client can still write the literal { balance: -100 }, or skip deposit and write { balance: account.balance - 200 }. Both type-check.

How do you take the data out of reach?

In three steps, all built from CPSC 110 ideas: 1. Restrict creation to one constructor function, which asserts the invariant. 2. Bind operations to the data: make the type’s properties functions (deposit, withdraw, getBalance), with no balance field. 3. Hide the state in a closure31: a function that keeps access to the parameters and definitions of the function that created it, even after that function has returned.

export function makeCounter(count: number): Counter {
  assert(count <= MAX_CAPACITY, "Invariant violation: Venue is full!");   // establish
  return {
    increment(): Counter { return makeCounter(count + 1); },  // every new state passes the check
    getCount(): number { return count; }                       // the only way to read count
  };
}

Because increment builds its result by calling makeCounter again, every state the counter ever reaches passes through that assertion. “There is no longer a balance property anywhere in the program for a client to read or forge.”

Why move on from this?

Because the language barely helps. The result “is not standard TypeScript” and can be hard to follow. Object-oriented programming gives the same pattern direct syntax (Chapter 10).

TipThink it through

What breaks if increment returns an object literal { increment, getCount } built by hand instead of calling makeCounter?

5. Arrays and Iteration

ImportantCore idea

Built-in sequences with ready-made traversals; the for of loop underneath for whatever they don’t cover.

What is an array?

Reading[] is an ordered collection whose elements all have the same type, accessed by position. It is zero-indexed32: day[0] is the first element, and day.length counts them. Each cell holds a reference33 to an object that lives elsewhere, not the object itself (Chapter 6).

How do you pick an operation?

By the result you want. Each takes a function saying what to do with one element:

Operation Output / Behavior
map34 A new array of the same length, each element transformed
filter35 A new array of the elements for which the function returns true
reduce(f, init)36 One value, carried through the array as an accumulator
find37 The first matching element, or undefined

None of them mutates38 the original array. Because map and filter return new arrays, they chain: day.filter(r => r.tempCelsius > 0).map(r => r.hour).

When is a loop the better tool?

When elements must be compared with each other, or no named operation fits, because each operation’s function sees one element at a time:

function hasRepeatedTemperature(day: Reading[]): boolean {
  for (const first of day) {
    for (const second of day) {
      if (first.hour !== second.hour) {                       // two different readings
        if (first.tempCelsius === second.tempCelsius) {
          return true;
        }
      }
    }
  }
  return false;
}

Otherwise prefer the named operation: “the named operations say what they are doing. Loops are for when you must control how it is done.”

What does JSON lose?

Everything that is not data. JSON39 is a text format with six kinds of value: four primitives (string, number, boolean, null), objects and arrays. It has no notation for a date, undefined, or a function, so JSON.stringify loses them without complaint. JSON.parse checks nothing: const readings: Reading[] = JSON.parse(text) is “hoped for, not checked” (Chapter 18).

TipThink it through

Why can’t hasRepeatedTemperature be written with map, filter or find alone?

6. Mutation and Side Effects

ImportantCore idea

Mutation adds time. “What does this variable hold?” now depends on when you ask, so reason by tracing state.

What does mutation add?

Time. A let variable can be reassigned; x = e evaluates e using current values, then stores the result. The state of a program is the value every variable holds at one instant, so order now matters: after let x = 1; x = x * 2; x = x + 3; x is 5, but swapping the two reassignments gives 8. Trace state with a trace table, or with the debugger for larger programs. The habit: declare everything with const, and change one declaration to let only when the compiler says it must change.

What does const actually freeze?

The name, not the object: after const reading = { hour: 6, tempCelsius: -4 }, reading.tempCelsius = -3 is legal; reading = {...} is not.

When do two names share one object?

Whenever an object is assigned. A primitive (number, string, boolean) is copied; an object variable holds a reference, and assignment copies the reference. After const s = r, s is an alias40 of r: two names for one object, so a change through either is seen through both. On objects, === compares identity: whether two names refer to the same object, not whether their contents match. filter builds a new array filled with the original’s references, a shallow copy41: changing frozen[0].tempCelsius changes day[0] too. push, pop and sort mutate the array in place.

Can a function change its caller’s data?

By mutating an object parameter, yes; by reassigning a parameter, no. Each argument is assigned to its parameter. A primitive arrives as a copy (pass-by-value). An object arrives as a copy of the reference, so changes through it reach the caller’s object. TypeScript’s precise behaviour is call-by-sharing42: “the dot is the difference.”

function calibrate(reading: Reading, offset: number): void {
  reading.tempCelsius = reading.tempCelsius + offset;      // caller sees it
}
function reset(reading: Reading): void {
  reading = { hour: reading.hour, tempCelsius: 0 };        // redirects the local arrow only
}

What decides how long things live?

Scope for names, reachability for objects. Under block scope43, a variable exists from its declaration to the end of the enclosing { }. An object lives while some chain of references from a live variable reaches it; garbage collection44 reclaims it after that. “Declare each variable in the smallest block that still spans every use of it.”

How do you test a side effect?

By checking state after the call. A side effect45 is any observable change a function makes besides returning a value: mutating an object its caller can see, reassigning an outside variable, or touching the outside world. A function with none is pure. A void signature says nothing about the effect, so document it (“Modifies the given reading in place”). With mutation, an invariant must be preserved by every operation, forever. A value that can never change after creation is immutable, and aliasing it is harmless.

TipThink it through

After const a = [{n: 1}]; const b = a.filter(x => true); b[0].n = 5; b.push({n: 9});, what are a and b, and why?

7. Asynchronous Effects

ImportantCore idea

Disk and network are millions of times slower than computing, so the single thread defers work instead of blocking.

Why not just wait for the disk?

Because waiting freezes everything. A blocking call does not return until the slow work finishes. A TypeScript program runs on one thread46 (an independent sequence of executing statements), so blocking it on I/O47 stops the whole program.

Instead it uses callbacks: functions handed to other code to run later. Finished work queues its callback, and the event loop48 takes callbacks from the front of the queue and runs each one to completion. So source order is not run order: console.log("A"); setTimeout(() => console.log("B"), 0); console.log("C"); prints A, C, B.

What is a promise?

A receipt for a value that does not exist yet. A Promise<T>49 starts pending, then settles once, either fulfilled with a T or rejected with an error, and never changes again. It is not a T: contents.length on a Promise<string> is a compile error.

What does await pause?

The function, not the program. While it waits, the thread runs other ready work. await is allowed only in an async50 function, which always returns a promise. “Asynchrony is contagious”: callers await it and must themselves be async, “all the way up.” A bare loadReport(); with the await forgotten compiles cleanly and does not wait. The course’s lint rules flag it.

One at a time, or all at once?

All at once for independent operations: start them all, then wait once. Calling a promise-returning function starts the work; awaiting it collects the result.

async function readAll(paths: string[]): Promise<string[]> {
  const pending: Promise<string>[] = paths.map((path: string) => readFile(path, "utf8"));
  return await Promise.all(pending);   // wait = the slowest read, not the sum
}

Promise.all returns results in the order supplied. It rejects as soon as any promise rejects, without cancelling the others. Await inside a loop only when iteration \(n\) needs iteration \(n-1\); the noAwaitInLoops lint rule flags the rest.

What about data from a web service?

It is unverified. In const report: StationReport = await response.json(), the annotation states an expectation that the compiler cannot verify: “the compiler’s guarantees stop at the program’s edge” (Chapter 18).

TipThink it through

A function calls loadReport but isn’t async. What does it get back, and why can’t it simply wait?

8. Designing for Failure

ImportantCore idea

Design expected failures as deliberately as successes: return them as values or throw them as exceptions.

What does returning a Result buy, and cost?

It puts the failure in the type, so “the compiler will not let them access .value without first checking .ok.” The cost: every layer between detection and handling must check and forward the failure. In the textbook’s enrolAll, four of eight lines only forward failures, breaking up the success path.

What does throwing do instead?

It skips the layers in between. A throw51 abandons the current function and passes the exception up the call stack. Each paused caller’s stack frame52 is removed in turn (the stack unwinds53) until a try/catch54 handles it.

Layers in between need no error code. TypeScript exceptions are unchecked: a signature never says what a function throws, so document it with @throws. An assert is a throw left deliberately uncaught.

function enrolStudent(catalogue: Section[], student: Student, ids: string[]): void {
  try {
    const sections = enrolAll(catalogue, student, ids);   // may throw from deep inside
    console.log("enrolled in " + sections.length + " sections");
  } catch (error) {                                       // the caught value has type unknown
    console.log("enrolment could not be completed:");
    console.log(error);
  }
}

A finally block runs on every path out of the try, so cleanup such as closing a file handle cannot be skipped. A thrown failure is not a value, so test it with checkError.

What must a catch never do?

Swallow the error silently. An empty catch turns a visible failure into a silent wrong answer. Catching only to report the failure and stop one operation is legitimate, and so is recovering, as sectionOrBackup does. Nor should exceptions serve as ordinary control flow: a throw never names its handler, so the path an exception takes can be read only from the dynamic view.

So which one?

Return a Result when the failure is an ordinary part of the operation that the immediate caller should always deal with. Throw when the failure should abort the current line of work and be handled well above. “Catch at the boundary where the program knows what to do”; a low-level library should almost never catch. Be consistent within a codebase.

TipThink it through

A file can be missing three layers down, and only main can respond. Return or throw? What changes if the immediate caller could use a default?

9. Validating Behaviour

ImportantCore idea

Real assertions, richer test bodies, both inputs and outputs partitioned, and coverage and regression to judge the suite.

Why does to.equal fail on two objects with the same contents?

Because to.equal compares with ===, which on objects tests identity (Chapter 6). For identity vs structural equality55 (same shape and values throughout), use to.deep.equal. checkExpect always compared deeply, so translate it to deep.equal when the expected value is an object or array.

Prefer a specific operator (to.include, to.have.length, to.have.members, to.be.closeTo): its failure message names the actual problem. expect(() => f()).to.throw("msg") needs the thunk, and passes only if the thrown message contains "msg".

What can a test body hold now?

Anything a block can. It can hold several assertions, its own setup (so no shared top-level state can make tests depend on their order), and multi-step driving. Order assertions general \(\to\) specific, so the first failure names the kind of fault:

const result = eligibleSections(catalogue, student);
expect(result).to.be.an("array");                                   // the right kind of value
expect(result).to.have.length(1);                                   // the right number
expect(result.map(s => s.id)).to.include("CPSC210");                // the right section
expect(result).to.deep.equal([{ id: "CPSC210", prerequisite: ["CPSC110"] }]);   // exactly right

Is partitioning the inputs enough?

No. When inputs are composite, the classes are combinations of fields (plan \(\times\) region \(\times\) title state). Partition the outputs too: empty, one, several.

Does 100% branch coverage mean the code is right?

No. Black-box tests come from the spec; white-box tests come from reading the code. Branch coverage56, the fraction of branches that at least one test runs, shows code the suite ignores. It cannot reveal a branch that is missing: a canPlay that never checks regional licensing still reaches 100%. Rerun the whole suite after every change to catch a regression57: a change that breaks behaviour that previously worked.

10. Building Abstractions (Classes)

ImportantCore idea

A class bundles state with the operations that maintain its invariant: Chapter 4’s closure pattern, with language support.

What is a class, in terms you already know?

A class58 is a template for a kind of value: the state every instance holds and the operations it provides. Each piece of the closure maps onto a piece of the class:

Closure Version (Chapter 4) Class Version
Variables closed over Fields59
The maker function The constructor60, run by new
The returned operations Methods61
Reaching state by closure Reaching state through this62

What the class adds is a name that is a type, a standard construction path through new, and operations grouped with the data by the language.

Who establishes the invariant, and who preserves it?

The constructor establishes it; each method preserves it. In Playlist, the current index must always point at a real song (or be -1 when the list is empty). remove repairs the index in every branch, so the caller never has to think about it. A field belongs in the class if its value must survive after a method returns, or be visible to other methods.

Is OO a different way of programming?

No. Functional, imperative and OO programming “are not competitors”. A method body is usually imperative, and a functional pipeline can run inside one. What changes is how the program is organised.

How do you test something with state?

Construct it, drive a sequence of calls, and assert on the resulting state. beforeEach builds a fresh object before every test, because one shared object would leak mutations between tests and make them depend on run order.

let playlist: Playlist;
beforeEach(() => { playlist = new Playlist(); });
test("the first song added becomes current", () => {
  playlist.add(songA);
  expect(playlist.current()).to.deep.equal(songA);
});

11. Decomposing Systems (Cohesion)

ImportantCore idea

Cohesion asks whether everything in a class belongs together. Single Responsibility at class level: one class, one invariant.

How does a god class happen?

One reasonable change at a time. Adding “recently played” to Playlist is easier than creating a new class, so the class ends up with two unrelated invariants. Repeat that, and you get a god class: one type that knows about and does everything. It is hard to change (no single invariant to reason about) and hard to use (no one can predict where a feature lives).

What does “single responsibility” mean concretely?

Under single responsibility (SRP), a class enforces one invariant, and every field and method exists to establish, preserve or observe it. In practice that means one cluster of invariants that constrain the same state and must hold together. A value object or stateless helper is cohesive around one concept instead.

How do you find and fix the problem?

Diagnose: name the invariant, then check each field and method against it. A field the invariant never mentions usually signals a second responsibility (an identity field like id is the exception). Design: invariants \(\to\) the state each constrains \(\to\) one class each \(\to\) have one hold the other and delegate \(\to\) name each class. “When it is hard to come up with a name, it is often a signal the split was poor.”

How do the pieces work together again?

Through composition63 and delegation. Composition means one object holds a reference to another (Playlist has a PlayHistory); delegation means the holder forwards work to it (play calls playHistory.record).

The class that needs a capability holds the one that provides it. A back-reference from PlayHistory to Playlist would bind the two in both directions. A field holding a collaborator does not break cohesion, because the class’s own invariant does not govern it.

Should every rule become a class?

No. Every split adds a name to learn and a unit to navigate. “No duplicate tags” can stay inline in Article if tag rules will never grow; extract a TagSet if they will.

12. Encapsulating What Varies

ImportantCore idea

Hide the representation so that only the class’s own methods can touch it, and the compiler enforces it.

Why isn’t a careful constructor enough?

Because public fields can be written by any code holding the object. list.invited.push("alice") twice breaks “no duplicates”, and list.capacity = -1 is legal.

What do private and readonly each control?

private64 controls who can access a member: only the class body. readonly65 controls when a field can change: only where it is declared or in the constructor. public is the default. TypeScript’s private is checked at compile time and erased at run time (JavaScript’s # fields stay private at run time). Encapsulated, GuestList’s constructor rejects invalid input, and every method preserves the invariant.

If the field is private, can the invariant still leak?

Yes, through references. A guests() that returns this.invited hands callers the private array itself, and everyone.push("alice") writes a duplicate straight into the list’s state. Return a defensive copy66 instead:

guests(): string[] {
  return this.invited.slice();   // a copy; mutating it cannot affect the list
}

slice() is shallow: safe for strings, which cannot be mutated, but not for an array of objects. structuredClone copies deeply, but returns class instances as plain objects without methods.

What does hiding buy later?

Freedom to change the representation. GuestList switched from string[] to Set<string> with no caller changed, and the Set makes “no duplicates” structural. Three habits keep that freedom: expose behaviour, not data; hide what is likely to change; add a public method only when a caller needs it.

How do you test what you’ve hidden?

Through the public methods, which may require design changes. A test needs controllability (it can drive the object into the state it wants) and observability (it can read back enough to judge the result). LoginThrottle read Date.now() internally, so testing the lock’s expiry meant waiting 30 seconds. The fix was to pass now: number as a parameter and add isLocked(now) and failureCount(). Add methods that report derived facts, never the raw representation.

13. Implementation Freedom

ImportantCore idea

A class’s representation is what it stores; its abstract value is what that means to a caller. A change to the representation is safe exactly when the new one denotes the same abstract values.

What does an object mean, versus what it stores?

The abstraction function (AF)67 maps each legal representation to the abstract value it stands for. It is many-to-one: ["alice","bob"], ["bob","alice"] and new Set(["alice","bob"]) are one guest list. The representation invariant (RI)68 is the class invariant you have been writing since Part 1: which representations are legal. Document both. Writing the abstract value down forces decisions, such as whether capacity is part of what a guest list is.

When are two objects “equal”?

Usually when they denote the same abstract value. That is equivalence, as opposed to identity (===). The language cannot check equivalence, so a class provides an equals method. An equals that walks two arrays position by position is wrong (it calls Alice-then-Bob and Bob-then-Alice different) and costs the class its freedom: it now depends on the array. Compare at the abstract level instead, using questions a caller could ask:

equals(other: GuestList): boolean {
  if (this.capacity !== other.capacity) { return false; }   // private is per class, not per object
  if (this.size() !== other.size()) { return false; }
  for (const guest of this.guests()) {
    if (other.isInvited(guest) === false) { return false; }
  }
  return true;
}

Keep it symmetric: a.equals(b) exactly when b.equals(a).

Which equality do includes, Set and Map use?

===, so for objects, identity. indexOf, includes, Set and Map keys all behave this way, never using your equals. That is why Playlist.remove removes only the exact Song object it was handed. Removing by identity is a decision, and the contract must state it.

Why make value objects immutable?

So that their meaning cannot change underneath whoever holds them. A value object is a class whose whole purpose is to be a value: a date, a money amount, a coordinate. An immutable object establishes its invariant once and returns new objects instead of changing (ImmutableGuestList.add returns a new list). Its abstract value never changes, so comparisons against it stay true. It also frees the class to build, share or cache returned values. (Contrast: const protects a binding and readonly protects a field; neither makes the object immutable.)

What does a generic class give up?

Knowledge of its member type. Roster<T> can only compare members with ===, so a Roster<Seat> lets the same seat in twice and breaks its own invariant. The fix is to pass equality in: new Roster<Seat>(400, (a, b) => a.equals(b)). “Flexibility is bought, not free”: every commitment a class declines is knowledge that must arrive some other way.

14. Defining Boundaries (Interfaces)

ImportantCore idea

Depend on a named contract, not on a class: an interface hides the class itself.

What is an interface?

An interface69 is a named type listing method signatures (all public, no bodies, no fields). It records what is promised and nothing about how. Convention: interface for a contract that classes implement and callers depend on; type for unions and the shapes of plain data. Interfaces are documented with care, because every member is a promise.

interface Notifier {
  send(message: string): void;
}
class EmailNotifier implements Notifier { /* private address; send(..) over email */ }
class SmsNotifier implements Notifier { /* private phone;   send(..) over SMS */ }

If TypeScript is structural, what does implements add?

A checked declaration of intent. Any object with a matching send already fits. With implements70, a missing or misspelled member fails at the class, where the mistake is, instead of at a distant call site.

Which type decides what you may call?

The apparent type. In const alerts: Notifier = new EmailNotifier("ops@example.com"), the apparent type is Notifier: what the compiler knows, from the static view. The actual type is EmailNotifier: the object that exists at run time. You may call only send, so any Notifier can stand behind the variable. That is the advice “program to an interface, not an implementation”.

How does a boundary help testing?

A test can hand the code a test double (or mock object): a simpler, observable implementation of the same contract. alertAll is tested with a RecordingNotifier that pushes each message to sent instead of sending email.

One big interface or several small ones?

Several small ones: the interface segregation principle (ISP). Delivery confirmation goes in its own Confirmable, and SmsNotifier implements Notifier, Confirmable. A large interface forces implementers to fake operations and makes callers depend on more than they use.

How does a generic class get the operations it needs?

Two routes, which trade against each other. Constrain the type, Roster<T extends Identifiable>, so every member has sameAs; then Roster<string> no longer compiles. Or pass the operation in (Chapter 13), which works for every type but obliges every caller. Constrain when you own the types and the operation is fundamental to them; pass it in otherwise.

15. Extending Behaviour (Polymorphism)

ImportantCore idea

One call, many behaviours, chosen at run time by the object’s actual type.

Where does shared behaviour go?

In an abstract base class, so it isn’t repeated in every class (don’t repeat yourself). An interface has no bodies; an abstract class mixes concrete members with abstract ones that each subclass must supply. It cannot be instantiated. protected members are visible to the class and its subclasses only.

abstract class BaseNotifier implements Notifier {
  public send(message: string): void {
    if (message.length === 0) { return; }          // shared rule
    this.deliver(this.decorate(message));
  }
  protected decorate(message: string): string { return "[ALERT] " + message; }
  protected abstract deliver(text: string): void;
}
class SmsNotifier extends BaseNotifier {
  // constructor calls super() first
  protected decorate(message: string): string { return super.decorate(message).slice(0, 160); }
  protected deliver(text: string): void { /* over SMS */ }
}

How can one call run different code?

By dynamic dispatch71: the method body that runs is chosen at run time from the object’s actual type, not its apparent type. Inside the inherited send, this.decorate and this.deliver run SmsNotifier’s versions. That is polymorphism72: one piece of code working with many types and behaving, for each, according to that type.

When may a subclass stand in for its base?

When it honours the contract: it demands no more (no stronger precondition), promises no less (no weaker postcondition), and preserves the base’s invariants. A send that also rejected messages containing whitespace would strengthen the precondition. One that silently dropped long messages would weaken the postcondition. The compiler catches neither, because the violation is in behaviour, not in types.

extends or implements?

extends for is-a: it inherits the implementation and the type, from one class at most. implements for can-do: type only, from any number of interfaces. A test double wants the type and none of the implementation, so it implements.

Then should everything inherit?

No: “composition over inheritance”. Polymorphism replaces a branch on a type tag, but combining features belongs to composition. For \(c\) channels in \(f\) formats, inheritance needs \(c \times f\) classes; holding a Formatter collaborator needs \(c + f\). A base class is fixed when the subclass is written, whereas a collaborator is chosen when the object is built. Subclasses depend on the base’s implementation, which causes the fragile base class problem: a harmless-looking change inside the base breaks subclasses that were never edited.

16. Growing Systems (Open/Closed)

ImportantCore idea

Code is open for extension and closed for modification (OCP) when new behaviour is added as new code, without changing existing code that already works.

What does it look like?

Adding a push channel is one new class. Notifier, BaseNotifier, the existing channels and alertAll are untouched:

class PushNotifier extends BaseNotifier {
  // constructor(deviceId) stores this.deviceId
  protected deliver(text: string): void { /* push to this.deviceId */ }
}
alertAll([new EmailNotifier("ops@example.com"), new PushNotifier("device-42")], "deploy finished");

The alternative, adding an else if to a function that branches on a channel string, reopens tested code. In practice the same tag is also branched on in formatting, validation and logging.

Why avoid editing working code?

Because every edit to tested code risks a regression (Chapter 9). Adding PushNotifier leaves the existing channels and their tests alone. “Closed” does not mean code never changes: bugs are still fixed. It means a foreseen kind of addition should not reopen working code.

Should every class be open?

No: no design is open on every axis. Put the boundary, an extension point73, where new variants will actually appear. Notifier is open to new channels, not to group delivery or scheduling. Abstractions for variation that never arrives are speculative generality74.

What must already be true for this to work?

Five principles at once: cohesion (Ch. 11), encapsulation (Ch. 12), implementation freedom (Ch. 13), small contracts (Ch. 14), and substitutability (Ch. 15). Open/closed “is not a seventh item”; it is what you observe when all five hold. Remove any one and the same addition gets harder. Underneath is the Dependency Inversion Principle (DIP)75: high-level policy depends on abstractions, not on concrete classes.

Why do the principles seem to conflict?

Because people predict change differently: “every design decision is an answer to the same question: what is likely to change?” The two possible errors are not equally expensive. An unnecessary abstraction is a small, permanent tax on every reader. A missing one costs a larger, one-time modification.

17. Coupling and Dependencies

ImportantCore idea

Coupling is the degree to which one part of a system depends on another. Cohesion is judged within a boundary, coupling between boundaries; both aim to keep change local.

Why does one change force others?

Because of hidden assumptions. WeeklyRecap read PlayHistory’s array directly. It assumed an array, most-recent-first ordering, Song elements and a title field, and none of these was in any contract. Adding timestamps to the history then broke code that had no interest in storage. That is the ripple effect. The practical test: “how much must you know about B in order to write or change A?”

How do you spot risky classes?

Draw the dependency graph: A depends on B if A constructs, holds, takes, calls or reads a B. Fan-in76 predicts how expensive it is to change; keep such classes small and stable, ideally interfaces. Fan-out77 predicts how fragile it is; keep such assembly classes few and at the edges. Every import is a dependency, and importing only a type commits you to less than importing a class you construct.

Are all dependencies equally bad?

No. From tightest to loosest: content (reading or writing another class’s internal state), common (shared mutable state that belongs to neither), control (a flag that picks the callee’s branch), stamp (a whole object when part would do), data (exactly the values needed). Move each dependency as far down the list as possible. Replace a boolean flag with named methods (weeklySummary), or with the value it stood for (summarySince(time)).

What does loose coupling look like in code?

Ask your neighbour; don’t walk through it. order.customer().address().city() needs three classes to be right. The Law of Demeter says a method should call methods only on itself, its fields, its parameters, and objects it creates, so write order.shippingCity(). Chains over one type, such as songs.filter(..).map(..), are fine. Under Tell, Don’t Ask (TDA), you tell an object what to do instead of extracting its state and deciding for it:

if (account.balance() >= amount) { account.setBalance(account.balance() - amount); }  // asks
account.withdraw(amount);                                                             // tells

How do you break a cycle?

Try these in order: reverse the direction of the question (the class that already depends asks); invert one direction with an interface (PlayHistory holds a PlayObserver, not a Playlist); or extract a third class for a policy that belongs to neither.

How do cohesion and coupling fit together?

As the two halves of separation of concerns (SoC): each concern (a rule, a responsibility, a reason to change) gets exactly one home. Tangling (many concerns in one place) is poor cohesion seen from inside a class; you fix it by splitting. Scattering (one concern spread across many places) is tight coupling seen from outside; you fix it by giving the concern one owner and a contract. Low coupling is not a goal by itself: merging everything into one class has zero coupling and is a god class.

18. Consuming Data and Services (APIs)

ImportantCore idea

Data from outside has no invariants. Convert it once, at the edge, into a typed value whose invariant holds, and keep the provider behind an interface you own.

What is an API, and how do the two kinds differ?

An API (Application Programming Interface)78 is a contract published by code you call but do not own. A library API runs in your process: it is fast, typed by the compiler, and changes only when you upgrade. A web service API runs on another machine: it takes milliseconds to seconds, can time out or half-complete, sends text that is typed only if you check it, and changes whenever the provider deploys.

Doesn’t a type annotation check the JSON?

No. JSON.parse and response.json() return any, which switches the checker off. as Shipment is “a claim, not a check”: it produces no code and cannot fail. Take incoming data as unknown, which cannot be used until converted, and convert it into a Result. Zod does this from a schema:

function toShipment(raw: unknown): Result<Shipment, string> {
  const parsed = ShipmentSchema.safeParse(raw);
  if (parsed.success === false) {
    return { ok: false, error: parsed.error.message };
  }
  return { ok: true, value: parsed.data };
}

Serialisation records fields only: no class, no methods, and a Map becomes {}. Rebuild objects with behaviour through their constructor, so the invariant is established again.

What can go wrong with a call?

Three things, each caught in a different place: 1. The call does not complete: fetch rejects. 2. An error status arrives: fetch does not throw on 404 or 500, so check response.ok. 4xx means the request was wrong and will fail again; 5xx means the service failed and a retry might work. 3. A 200 carries the wrong data: the converter catches it.

Latency makes every caller async, and a response is stale the instant it arrives. Retry only idempotent79 calls, ones where doing it twice has the same effect as once (GET, PUT), and space the retries out.

How do you keep the provider out of your design?

Own the contract (CarrierClient), and write one adapter per provider: a class that implements your interface and knows one provider’s URLs, JSON and vocabulary. ParcelTracker receives its adapters through its constructor. Supplying a dependency from outside instead of constructing it is dependency injection (DI). Gather that construction in one place at the program’s edge, the composition root, the only code that names concrete carriers.

19. Designing APIs

ImportantCore idea

A published API is close to permanent and its users are engineers: keep it small, easy to use correctly, and hard to use incorrectly.

Why export so little?

Because of Hyrum’s Law80: with enough clients, every observable behaviour will be depended on by somebody, whatever the contract says. Adding later is easy; removing breaks clients. Declare the surface in one index.ts. Don’t export internal types for convenience, and don’t let a dependency’s types (such as Zod’s) into your signatures.

What makes misuse hard?

Design so the compiler catches the mistake. track(carrierId: string, trackingNumber: string) lets the two strings be swapped silently; an options object, track({ carrierId, trackingNumber }), or distinct value types prevent it. Also: descriptive names, consistency across the surface, and one documented meaning for absence.

Why tagged errors instead of messages?

Because clients branch on kind, which you promise, not on message text, which you don’t. That leaves the wording free to change:

export type TrackingError =
  | { kind: "malformed-tracking-number"; reason: string }
  | { kind: "unknown-tracking-number" }
  | { kind: "carrier-unavailable"; carrier: string };

Documentation is the API for a client. State what clients may not rely on (“may be out of date immediately”), because a non-promise keeps you free, for example to add caching later.

Which changes break clients?

  • Safe: A new operation, an optional parameter, accepting input you used to reject; adding a field to a returned object is usually safe.
  • Breaking: Renaming, removing, a required parameter, rejecting input you used to accept, changing a field’s type, and adding a failure case. The dangerous ones compile: tightening validation, changing a field’s meaning, reordering results, rewording a matched message.

How do you change it anyway?

Signal it with Semantic Versioning (SemVer)81: major.minor.patch, with a major bump for any breaking change. Remove in steps: @deprecated with the replacement named (minor release), wait across several releases, then remove (major release).

20. Code Quality and Refactoring

ImportantCore idea

Refactor to make the upcoming change easy: change structure, not behaviour, with the suite checking every step.

If the tests pass, is the code good?

Not necessarily. External quality (does it do what it should?) is what users see and what tests measure. Internal quality (can a person read, reason about and safely change it?) is invisible until a change is needed. The two are independent.

What are smells really pointing at?

A code smell is a surface sign of a deeper design problem, a hint and not a rule. Most smells reduce to tangling or scattering (Chapter 17). Tangling is cured by splitting. Scattering is cured by consolidating. Record deliberate technical debt82 where the next maintainer will look, because undocumented debt looks like intended design.

How do you know you changed only structure?

By running the suite before and after. Refactoring83 changes structure and preserves behaviour; never combine it with a feature, a bug fix or a rewrite in one change. Run the suite first, make the change, run it again. For untested code, first write a characterisation test that records what the code does now.

How do you refactor safely?

A sequence of small named moves (rename, extract function, extract class, move method, inline, replace conditional with polymorphism), with step \(\to\) test \(\to\) commit after each. Stop once the change you came to make is easy: “make the change easy, then make the easy change.”

21. Debugging and Fault Localization

ImportantCore idea

Debugging is a process, not a talent: reproduce, localize, fix, validate.

What are you actually looking for?

The fault84: the defect in the code, the thing you eventually edit. When it executes it produces an error85, an incorrect state while running, usually invisible. That may surface as a failure86, the externally visible misbehaviour a user reports.

\[\text{Fault (code)} \longrightarrow \text{Error (state)} \longrightarrow \text{Failure (symptom)}\]

Why reproduce first?

Because nothing else is actionable until you can trigger the failure on demand. Make the reproduction deterministic: pass time and randomness as parameters, replace network calls with test doubles, reset state between tests. Make it minimal: everything you remove without losing the failure is somewhere the fault is not.

How do you narrow it down?

Use the scientific loop: state a hypothesis precise enough to be false, predict, observe, keep or discard. Follow the dependency graph backwards, start from what changed, and bisect (git bisect finds the commit where behaviour changed). Tools: debugger, print statements, and assertions.

Where does the fix go?

At the fault, not the symptom. Ask three questions: what else could this fault produce, at what level does it live, and why was it possible? Then write the reproduction as a regression test, watch it fail, fix, and rerun the full suite.

22. Adding New Features

ImportantCore idea

What a feature costs depends far less on the feature than on whether the design anticipated it.

Is the request the spec?

No; it states a need. Turn the request into a user story with acceptance criteria. Ask who it is for and what they will do differently, what success looks like, and what is explicitly not included. “This should not be built here” is a legitimate answer.

Is there a place for it already?

Look for an extension point (or seam): an interface with several implementations, an abstract base, a collaborator passed through a constructor, or the composition root. A sixth carrier lands on one: one new class, CarrierFClient implements CarrierClient, plus one line at the composition root. No existing file or test changes.

And if there isn’t?

Create it first. Forcing delay notifications into locate(trackingNumber, notifier?) violates command-query separation (CQS) (a method either returns a value or changes something, not both). Instead, commit 1 adds an observer interface; with no observers the behaviour is unchanged. Commit 2 adds the concrete observer, plus one line at the composition root.

When is it done?

When the new behaviour is tested, including failure cases; the whole suite passes; documentation and contracts are updated; no new smells appear; and “the next feature is not harder because of this one.”

How the Parts Answer the Question

The textbook’s closing argument is that invariants, cohesion, encapsulation, interfaces, polymorphism, low coupling, validated boundaries, small published surfaces and a regression suite “were each introduced for their own reasons, but every one of them was ultimately about the resistance of a design to change.”

  • Part 1: Know at once whether a change broke anything. Types, tests and assertions each cover the others’ gaps (Ch. 3), and the regression suite rechecks everything after each change (Ch. 9).
  • Part 2: Keep a change behind a boundary. A class that protects its invariant can be changed without auditing the program (Ch. 10–12); a contract lets whole classes change or be added (Ch. 13–16).
  • Part 3: Keep a change local and its cost visible. Low coupling limits the ripple (Ch. 17); edges isolate what you don’t control (Ch. 18–19); refactoring makes room for a feature on an extension point (Ch. 20–22).

Objection. All this structure (interfaces, extra classes, extension points) is itself code to read and change, so it can make changes dearer.
Answer. The textbook agrees and limits it. An unnecessary abstraction is a small, permanent tax, so build only for variation you have evidence for (Ch. 16). Define an interface only when change is likely, a second implementation is plausible, or a test needs a stand-in (Ch. 17). Don’t refactor code nobody needs to change (Ch. 20).

  14. Tagged Union: A data structure that can hold one of several distinct shapes, labeled with an explicit tag (like kind) so you always know which shape is inside.↩︎

  15. Generics: Type placeholders (like List<T>) that let you write one reusable structure that works on any data type, like a shipping box that can hold shoes, books, or toys.↩︎

  16. Recursion: A technique where a function solves a big problem by calling itself on smaller and smaller sub-problems until reaching a simple stopping condition (base case).↩︎

  17. Narrowing: Using an if-check to narrow down a broad set of possible types to one specific concrete case.↩︎

  18. null: An intentional placeholder value meaning “deliberately empty” (an intentionally emptied box).↩︎

  19. undefined: The default state of a variable that was created but never assigned a value (a box that was never filled).↩︎

  20. Invariant: A fundamental truth or rule about an object’s data that must strictly hold true at all times (e.g., “enrolled count cannot exceed room capacity”).↩︎

  21. Preconditions: Mandatory rules the caller must guarantee before calling a function (like having money in the account before withdrawing).↩︎

  22. Postconditions: Guarantees the function promises to deliver when it completes, provided all preconditions were met.↩︎

  23. Contract: A formal agreement between caller and function detailing rights, prerequisites, and promises.↩︎

  24. Stub: A temporary, intentionally broken or incomplete placeholder function used to verify that new tests fail before writing real code.↩︎

  25. Equivalence Classes: Grouping all possible inputs into categories expected to trigger the same behavior, so you only need to test one representative from each.↩︎

  26. Boundary Values: Inputs sitting right on the extreme edges between categories (e.g., minimum, maximum, 0, or off-by-one points), where bugs almost always hide.↩︎

  27. Assert: A runtime tripwire. If its condition is false, it immediately halts the program because an impossible internal bug occurred.↩︎

  28. Result<T, E>: An explicit return type that cleanly separates success (containing data of type T) from an expected error (containing error information of type E).↩︎

  29. Established: Made strictly true right from the start when an object is first created by its constructor.↩︎

  30. Preserved: Maintained as true across every single operation or method that modifies the object.↩︎

  31. Closure: A function bundled together with the surrounding variables from where it was created, keeping those variables private and protected from outside tampering.↩︎

  32. Zero-Indexed: Counting elements starting at position 0 instead of 1, so the first element is at [0] and the last is at [length - 1].↩︎

  33. References: Memory addresses pointing to where data lives, like writing someone’s street address on paper rather than cloning their house.↩︎

  34. map: An operation that transforms every item in an array one-by-one, producing a new array of the exact same length.↩︎

  35. filter: An operation that inspects each element and keeps only those that pass a true/false condition.↩︎

  36. reduce: An operation that folds or combines an entire array of items down into a single final value (like summing numbers).↩︎

  37. find: An operation that searches through an array and returns the very first item matching a condition.↩︎

  38. Mutate: Modifying or overwriting existing data directly in memory rather than creating a new copy.↩︎

  39. JSON (JavaScript Object Notation): A universal text format used to store and transmit structured data across different programs and web servers.↩︎

  40. Alias: Having multiple variable names pointing to the exact same object in memory. Modifying the object through one name alters it for all aliases.↩︎

  41. Shallow Copy: Creating a new outer container, but filling it with the exact same memory references as the original (the objects inside are still shared).↩︎

  42. Call-by-Sharing: Passing a reference to an object into a function. The function can edit properties inside the object, but reassigning the variable name itself does not affect the caller.↩︎

  43. Block Scope: The lifespan and visibility of a variable, strictly restricted to the enclosing curly braces { } where it was defined.↩︎

  44. Garbage Collection: The computer automatically reclaiming memory from objects that can no longer be reached by any variable in the program.↩︎

  45. Side Effect: Any observable change a function causes outside its return value (like modifying an input argument, writing to a file, or updating a display).↩︎

  46. Thread: A single execution line running one instruction at a time (like a single chef in a kitchen). A single thread can only do one task at a time.↩︎

  47. I/O (Input/Output): Communication between the CPU and the outside world (hard drive, internet, screen), which takes millions of times longer than pure computing.↩︎

  48. Event Loop: A scheduler that constantly checks if asynchronous tasks (like disk reads or web downloads) have finished, running their waiting callbacks when the main thread is idle.↩︎

  49. Promise: A placeholder or receipt for a future value that has not arrived yet, which will eventually resolve with data or reject with an error.↩︎

  50. async/await: Keywords that pause a function until a Promise finishes, without freezing the entire program or thread.↩︎

  51. throw: Halting normal execution immediately and signaling an emergency error that must be handled higher up.↩︎

  52. Stack Frame: The memory block holding the local variables and execution state of one currently active function on the call stack.↩︎

  53. Unwinding the Stack: Tearing down active function stack frames one by one during an exception until a matching catch block is found.↩︎

  54. catch: A safety block designed to intercept and handle errors thrown from within a try block.↩︎

  55. Identity vs Structural Equality: Identity asks “are these the exact same memory address?”, whereas Structural (deep) asks “do these two separate objects have identical contents?”.↩︎

  56. Branch Coverage: The percentage of decision branches (if/else paths) in your code that were executed during your automated test suite.↩︎

  57. Regression: An unintended bug introduced into previously working features when making a new change or fix.↩︎

  58. Class: A blueprint or template defining the state (fields) and behaviors (methods) that its instantiated objects will have.↩︎

  59. Fields: Variables that live inside an object, storing its private internal data.↩︎

  60. Constructor: The specialized setup function that creates and initializes a new object, checking all initial rules.↩︎

  61. Methods: Functions attached to an object that have special access to read and modify its internal fields.↩︎

  62. this: A keyword inside a class method referring to the specific object instance currently executing the code.↩︎

  63. Composition: Assembling complex functionality by holding references to other helper objects (“has-a”) rather than inheriting from a parent class (“is-a”).↩︎

  64. private: An access modifier restricting visibility so only code inside this exact class can touch that field or method.↩︎

  65. readonly: A modifier ensuring a variable or field can only be assigned once and never overwritten later.↩︎

  66. Defensive Copy: Duplicating an incoming or outgoing array/object so outside code cannot accidentally corrupt your internal private data through an alias.↩︎

  67. Abstraction Function (AF): A conceptual map explaining how the messy internal storage fields correspond to the clean mathematical concept the user sees.↩︎

  68. Representation Invariant (RI): A strict rule defining which internal data configurations are valid representations of the abstract value.↩︎

  69. Interface: A pure contract or specification of method names and types that an object promises to support, without specifying how they are implemented.↩︎

  70. implements: A formal declaration that a class commits to providing every single method and property demanded by an interface.↩︎

  71. Dynamic Dispatch: The runtime lookup where the computer checks the actual object class at the moment of the call to choose which version of a method to run.↩︎

  72. Polymorphism: “Many forms”—the ability of different classes to respond to the exact same method call in their own specialized ways.↩︎

  73. Extension Point: A designated hook or interface in your architecture designed to let new classes plug in cleanly without modifying existing code.↩︎

  74. Speculative Generality: Adding unnecessary flexibility, hooks, and complex abstractions for hypothetical features nobody has asked for.↩︎

  75. Dependency Inversion Principle: The rule that high-level business logic should depend on abstract interfaces rather than concrete, low-level implementation details.↩︎

  76. Fan-in: The number of other classes that depend on this class. High fan-in means changes here will ripple across the entire system.↩︎

  77. fan-out: The number of other classes that this class relies on. High fan-out means this class is fragile because it depends on many outside things.↩︎

  78. API (Application Programming Interface): A documented doorway allowing different software programs to talk to each other and exchange data.↩︎

  79. Idempotent: An operation that produces the exact same outcome whether executed once or repeated ten times in a row (like pushing an elevator call button).↩︎

  80. Hyrum’s Law: The observation that with enough users, every observable quirk of a system will be relied upon by someone, making changes risky.↩︎

  81. SemVer (Semantic Versioning): The standard versioning convention Major.Minor.Patch (e.g. 2.1.4), where breaking changes force a Major version bump.↩︎

  82. Technical Debt: The future cost of taking quick-and-dirty shortcuts today, which makes adding future features progressively harder and slower.↩︎

  83. Refactoring: Restructuring and cleaning up internal code without changing any of its external behavior or results.↩︎

  84. Fault: A static bug, defect, or mistake written directly in the source code.↩︎

  85. Error: An incorrect, diseased intermediate internal runtime state resulting from executing a fault.↩︎

  86. Failure: An externally visible deviation from expected behavior or specification (what a user or test actually witnesses).↩︎
